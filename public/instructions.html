DyCAD — Instructions

DyCAD is a browser-based enterprise architecture modeling and simulation tool, with optional Streams — a tagging and pattern-generation layer that lets you describe and regenerate whole business flows, not just draw individual boxes and lines. This page is a working reference, not a tutorial — skim the headings, come back to the section you need.

1. The Data Model

Five kinds of record make up everything in DyCAD. Understanding how they relate is the single most useful thing to know before you start clicking around — most "why did that happen" moments trace back to this.

RecordWhat it isKey fields
Part A "thing" in your architecture — an actor, capability, application, data entity, technology component, etc. Parts are shared: the same part can appear on many views. Type (from the toolkit), Label, Model, Description, Note, Script (see Simulation)
Connector A relationship between two parts (Serves, Realizes, Triggers, Composition, etc.). Also shared across views the same way parts are. From, To, Relationship type, Model, Note
View A diagram — what you actually look at and edit. A view doesn't contain parts or connectors directly; it contains placements of them (see ViewMember, next). Name, View Type, spacing/routing settings, display toggles
ViewMember One part or connector's appearance on one specific view — its position, color, and whether it's flagged "external." The same underlying part can have a different position and color on every view that shows it, because each view has its own ViewMember for that part. x/y position, Fill Color, Order, Linked View Name, External flag
Model A namespace parts and connectors belong to — use it to separate as-is vs to-be architectures, different business units, or anything else you want scoped independently. Simulation runs per-model. Just a name — parts/connectors reference it

Why this separation matters in practice: if you edit a part's Label or Type from the property panel, that change shows up on every view that part appears on — you're editing the shared thing, not just this drawing of it. If you only want to change how it looks on this one view (position, color), that's the ViewMember-level fields at the top of the property panel, described more in Property Panels below.

Streams

A Stream is a tag you attach to parts and connectors to say "these belong to this named business flow." Streams are what the Generate Stream and Remap commands key off of — a stream template describes the shape a flow should take (which element types, in what order, how they connect), and DyCAD builds or reorganizes a set of tagged nodes to match it. This is the part of DyCAD that goes beyond standard ArchiMate drawing: instead of manually placing and connecting a dozen boxes for a business capability flow, you generate the whole pattern from a template and a few names.

2. Views & Layout

View types

Every view is one of a small set of types, chosen when you create it:

  • Free form — an open canvas, place things anywhere. Most modeling happens here.
  • Section-based views (e.g. "Business function organization," "empty with 1 section") — the canvas is divided into fixed, named sections (a grid of cells), each restricted to certain element types. Dragging a node snaps it to the nearest valid cell in the section it's dropped near; dropping onto an occupied cell finds the next free one, and a completely full section automatically grows by a row rather than let two nodes overlap.

File > Export View as Image (SVG or PNG) reproduces what's on the real canvas, including section boxes and their header labels for a section-based view — not just the nodes and connectors inside them — and the view's own Connector Routing/Stream Connector Routing choice (straight, direct, or Manhattan, including routing around other nodes in the way), not always a fixed curve or straight line regardless of that setting. Run the same command while the 3D View tab is active and it exports a PNG snapshot of the current 3D scene instead — whatever rotation/zoom/filters are showing right now — with no SVG option (there's no meaningful vector serialization of a rendered 3D scene).

Remap

Reorganizes a view's layout. Six patterns:

  • Default — groups nodes by stream into rows, following the stream template's own ordering.
  • None — a plain sorted grid, no stream grouping.
  • Layered — rows come from directed connector-graph structure instead of stream/ element-group membership: a node's row is the fewest hops any real connector justifies from a root (a node nothing points into). Useful when the grouping you want doesn't match custom.json's element groups — e.g. a Business Function and its own Processes normally land in the SAME row under Default (same group), but Layered puts the Function a row above its Processes instead, following the actual connector chain. Two types can still end up sharing a row under Layered if each is reachable from a root in the same number of hops, even when a direct connector also links them to each other. No column-limit option (every row is exactly one graph layer, however wide it ends up).
  • Force-directed — an entirely different approach: connected nodes are pulled together and placed in directly adjacent grid cells; unconnected clusters are packed into their own separate regions. Good for "just show me how this is actually connected" rather than a prescribed row order. Doesn't use sort order or column limits, since the layout is driven by connectivity instead.
  • Centralize in Clusters — like Force-directed, but instead of finding just ONE central hub for a whole connected diagram, it repeats the pattern: every locally most-connected node gets centered with its own single-connection neighbors placed directly around it, and this repeats across the diagram, tiling the resulting hub clusters together. Especially useful for an ERD, which is often one single connected web of tables end to end — Force-directed would give it exactly one hub for everything, while Centralize in Clusters breaks it into several readable table-and-its-related-tables groupings instead. Clusters that connect to each other are automatically packed near one another, and any node that still ends up sitting on top of an unrelated connector line gets nudged aside — but a table that connects to more than one cluster can't always land adjacent to every cluster it touches, the same kind of unavoidable 2D-layout tradeoff Force-directed already makes for cycles.
  • Custom (Script Console) — hands placement completely to a function YOU write, named CustomRemap_<Name>(ctx), in the Script Console text (Advanced menu) — the same place main()'s starter scripts and dataAutoFill() already live. Selecting this pattern reveals a second dropdown listing every such function found there; pick one and Remap calls it with a ctx holding this view's own parts/connectors, node size, and spacing — see "Node Scripting" below for the full ctx shape, including a grid-coordinate convenience layer (ctx.gridToXY(row, col), setRowGap/setColGap) so you can think in rows and columns instead of hand-computing canvas pixels. The shipped default, CustomRemap_Example, groups parts onto one row per element type using exactly that. Like Force-directed/Centralize in Clusters, it doesn't use sort order, column limits, or Edge Assignment — the function decides every position itself.

Remap also has an "only remap filtered nodes" option — combine it with the Stream, Type, or Section filter to reorganize just a subset of a busy view without disturbing everything else. A sibling "only remap selected nodes and their connectors" option does the same thing keyed off whatever's currently selected on the canvas instead of a filter — check it before running Remap and only the selected nodes (and the connectors between them) move; everything else stays exactly where it was. Works with every pattern, and combines with "only remap filtered nodes" too (a node has to satisfy both when both are checked). Either restricted option's result is anchored back at the moved nodes' own original position, not the view's usual top-left starting point — so a small remapped group lands where you had it, instead of landing on top of whatever else already occupies that corner of the view. A full, unrestricted Remap (neither box checked) is unaffected and still starts from the view's normal origin as always.

Edge Assignment (Default/None/Layered patterns only) pins an element type — scoped to the types actually placed on the current view — to a numbered row or column slot (1-5) along the Top, Bottom, Left, or Right edge of the whole layout instead of its normal stream/element-group position, e.g. Business Actors on Left 1, Business Functions on Top 1, Data Entities on Bottom 1. Slot 1 sits closest to that physical edge of the layout; higher numbers step inward toward the middle grid — assign two different element types to, say, Left 1 and Left 2 to give each its own separate column instead of sharing one. A slot with nothing assigned to it is skipped automatically (Left 1 and Left 3 used, nothing on Left 2, produces two adjacent columns with no gap) — check Blank slots below the type list for a specific edge/number to force that slot to stay reserved but empty instead, opening up a deliberate gap. Members within one slot are ordered by the same Sort priority keys as the main grid by default, so picking Connection Order there gives "natural flow" within that slot too — unless Minimize Crossings (below) is also checked, in which case a slot's order comes from that instead, so e.g. a Data Entity connected to two different Capabilities correctly lands between the two Entities that only connect to one of them each, rather than wherever alphabetical order happens to put it. Minimize connector crossings and Minimize connector length (also Default/None/ Layered only) run two further passes, in that order. Minimize connector crossings reorders nodes sideways within their own row (or, per the above, an Edge Assignment band) to reduce how often connector lines cross. Minimize connector length then nudges nodes toward similar positions but closer — sliding each node toward the average position of whatever it's connected to (without changing which row it's on, or the left-to-right order crossing minimization just settled on), so connected nodes end up nearer each other and connector lines straighten and shorten. Both passes apply to the middle grid AND to Edge Assignment bands — a part pinned to Top/Bottom/Left/Right can get reordered within its band and slides along its own edge to align with whatever it's connected to in the middle grid, not just the plain, evenly-spaced band position it'd otherwise get. Both are heuristics, not guaranteed-optimal, but they noticeably clean up busy views — and combine well, since crossing reduction decides ordering first and length minimization then tightens the actual spacing. None of the three options do anything on the Force-directed, Centralize in Clusters, or Custom patterns, or a section-based view, since none of them have a free row/column to bias.

Remap's own choices (pattern, options, sort priority order) are remembered as your defaults the next time you open it on any view — and reopening it on the SAME view you last ran it on brings back that view's own settings specifically (pattern, both minimize checkboxes, Edge Assignment, template, which Custom function was selected — not just sort order), ahead of the general cross-view default a brand-new view still falls back to. The Stream Template you pick is remembered too, and shared as the default across every dialog that offers one (Remap, Generate Stream, Smart Check View's Auto-Complete Streams) — so you only have to pick it once. A Preset row at the top of the dialog can also save the current field values — including Edge Assignment, Minimize Crossings, Minimize Connector Length, and the selected Custom function — as a named, reusable preset (Save As…) or load one back in (Load). Presets are Local Settings, not part of the model — like Insert Smart Stream's own presets, they never end up in a saved JSON file, but do travel with File > Save/Load Local Settings and auto-apply from this browser's cache on reload. Also callable directly from a batch script — see Script Console below. Right-clicking the Remap button (instead of left-clicking to run it) copies a ready-to-paste remap(app, tab, {...}) call, matching whatever the form currently holds, to your clipboard — handy for pasting into the Script Console to replay the exact same settings later without re-filling every field by hand.

Connector routing

A per-view setting (Root Properties on the view, or the view's own property panel) with three styles:

  • Default — a gentle curve or straight line, no obstacle avoidance.
  • Direct — routes around any node in the way with straight segments, falling back to the default curve when nothing's actually blocking the path.
  • Manhattan — same idea, but every segment is horizontal or vertical (right angles only).

Routing only looks at obstacles near each connector's own path, not the whole diagram — this keeps large views fast, but means it won't reroute around something on the far side of the canvas that isn't actually in the way.

Spacing

The Spacing +/- control scales the gap between every node uniformly, keeping their relative arrangement intact — it doesn't reflow the layout, just stretches or compresses the space between what's already there. This is separate from node size: a new view's nodes default to 156x55 (the base 130x46 box, scaled by the node size multiplier below) — bigger than a stretched gap between small boxes, so labels are less likely to get clipped in the first place. The Redraw command (see Commands below) still auto-fits an existing view's node size to its actual content on demand.

With 2 or more nodes selected on a freeform view, Spacing +/- switches targets entirely: instead of scaling the whole view's spacing (and instead of touching the view's own remembered Spacing value at all), it scales just the selected nodes apart from or together toward their own center — handy for spreading out or tightening up one crowded cluster without disturbing anything else on the canvas. Clear the selection (or select fewer than two nodes) and Spacing +/- goes back to its normal whole-view behavior. Not available on section-based views, where node positions come from the section grid itself rather than free x/y.

The small icon between the Spacing − and + buttons (↔ / ↕ / ↔↕) is a direction toggle — click it to cycle between Horizontal only, Vertical only, and Both. It only changes anything while 2 or more nodes are selected: with Horizontal only picked, Spacing +/- moves selected nodes apart/together left-right and leaves their vertical position alone; Vertical only does the reverse. The whole-view fallback (fewer than 2 selected) always adjusts both directions together, same as before this toggle existed. Also available as the "Spacing Direction" field in the view's own property panel (nothing selected on the canvas), alongside Spacing itself.

The node size multiplier (default 1.2) is configurable via File > Load Local Settings, alongside Max Script Entities — see Simulation Scripting below for how that file and its localStorage caching work. It only affects views created after it's set; it doesn't resize anything already on screen.

3. Commands

Available from the Commands panel (left sidebar) when a canvas view is active, and via right-click on the canvas. Availability depends on what's selected — greyed out means the current selection doesn't apply.

CommandWhat it does
Generate StreamBuilds a whole flow from a stream template — pick a template, name the function/capability/entity, and DyCAD creates and connects the matching set of parts for you (reusing any part that already matches by name/type instead of duplicating it). Stream Name accepts a new name or an existing one — picking an existing stream prepopulates the other fields from it (and switches to an Application Capability-capable template if that stream has one), so you can add to or regenerate a stream without retyping everything.
Duplicate StreamClones an existing stream (a part that already has a stream tag) under a new name — useful for variations on an existing flow without starting from scratch.
Split NodeCreates a sibling copy of the selected part and rewires its outgoing connectors to the new copy — handy for splitting one node's responsibilities into two.
Level UpOpens a new parent view containing this view's nodes, letting you build a higher-level diagram that this one nests under. Exception: if exactly one Data Entity Details node is selected, Level Up instead creates (or, if one already exists, just opens) its Data Entity parent — see Data Modeling below.
Level DownPushes two or more selected nodes into a new sub-view, replacing them here with a single node linked down to that detail view (double-click to navigate down; double-click the linked placeholder to come back up). Double-clicking a single node that has no linked view yet does the same thing for just that one node: creates a new sub-view, links this node down to it, and gives the sub-view a genuinely new part of the same type/label to build the decomposition around (not the same part reused — renaming or retyping it there won't rename the node up here) — its immediate neighbors carry down too, as external context nodes. A structural Composition link (parent part → new anchor) is created behind the scenes so Smart Check View/Node can keep the two levels in sync later — see below.
Level ItFreeform views only. Fixes a node that's connected directly to a neighbor several steps away in the current stream template's chain — e.g. a Data Data Entity wired straight to a Business Process, skipping the Application Capability that actually belongs between them. Silently (no dialog) replaces the selected node with an EXISTING node of the correct in-between type that shares one of its own streams — never creates a new one; if none exists, nothing changes and a toast explains why. Works either direction: right-click whichever of the two connected nodes is out of place. The original node and connector are never deleted from the model (only removed from this view), and the original node stays if it still has other connectors here too.
MergeCombines two or more selected nodes into one, keeping their combined connections.
Copy / PasteStandard copy-paste for selected nodes, within or across views.
RemapSee Views & Layout above.
RedrawRecalculates the best node size for the current view based on its content.
Add ExistingBrings parts that already exist elsewhere in the model into this view (optionally including their connectors), instead of creating duplicates. On a section-based view (e.g. Org Chart), right-clicking inside a specific section pre-filters the list to types that section actually allows, and the parts you add land in that same section — not just wherever the first type-matching section elsewhere in the view happens to be. Right-clicking elsewhere on the view (outside any one section) pre-filters to the union of every section's allowed types instead, and falls back to whichever section you last clicked the header of (if any) for placement. A freeform view is never filtered.
Populate From TemplateFills a view from a page template matching its view type (e.g. a full "Enterprise Functions" section layout) — reuses existing parts by label/type/model match where possible rather than duplicating them.
Insert Smart StreamFreeform views only. Traces a chain of existing parts into the current view by element type: pick a Connector Type (Connectors or Streams), a Starting Element type — which populates a Starting Element Instances checklist of that type's actual parts, defaulting to all checked, so you can narrow the trace down to specific starting part(s) rather than every part of that type — a Direction (Upstream, Downstream, or Both), an optional Ending Element type, how many Children Levels to follow (blank = unlimited), and an Element Types to Show checklist (scoped to only the element types actually present in the current default model, and defaulting to all of them checked). Starting from the checked instance(s), it follows connectors of the chosen Connector Type in the chosen direction(s) up to the level limit — a part matching the Ending Element type is still included but doesn't itself propagate any further, so other branches keep expanding independently. The result is then narrowed to only the checked element types (a connector is only placed if both its endpoints survived that narrowing), and only genuinely new parts/connectors get added — anything already on the view is left alone. Since only real, existing connectors are ever placed, they keep whatever line/arrowhead styling their own relationship already has. When one or more hidden (unchecked) element types sit between two shown parts — e.g. Business Function shown, Application Capability shown, but Business Process hidden in between — a genuine new "derived" connector is added directly linking the two, so the relationship isn't lost just because the type in the middle is hidden; its Note field records which hidden type(s) it stands in for. A derived link is created as both a Connector ('c') and a Stream ('s') version — but only the one matching this trace's own Connector Type setting is actually placed on the view being built here; the other still exists in the model (e.g. for the 3D View's own Connector Type filter, or a later Smart Check). The Connector ('c') version's own relationship is normally whatever the first real hop's own relationship was, but falls back instead — to that element-type pair's own default relationship where one is defined, else plain Association — whenever that traced value isn't actually a valid relationship for the pair (e.g. a chain discovered by tracing Streams would otherwise leave a Connector labeled "Stream"); the Stream ('s') version's relationship is never affected by this. No derived connector is added where a real, direct one already exists, and re-running the same trace never creates a duplicate. Also callable directly from a batch script — see Script Console below. A Preset row at the top of the dialog can save the current field values as a named, reusable preset (Save As…) or load one back in (Load) — presets remember the starting element by type and part label(s), not raw part ids, so they still resolve sensibly against a regenerated or different document later (any label that no longer matches a real part is simply left unchecked on load). Presets are Local Settings, not part of the model — they never end up in a saved JSON file, but do travel with File > Save/Load Local Settings and auto-apply from this browser's cache on reload, same as the Script Console's own text. One preset, "StreamSet1", ships out of the box, matching the Script Console's own BatchScript_InsertSmartStreamExample.
Smart Check View(Advanced menu) Repairs gaps between a view and the underlying model: adds any connector that should exist between two nodes already on the view, and optionally pulls in nodes connected to what's already there (with a Levels setting for how many hops to follow). Every change it makes is written to the Message Log, and it notes what it created directly on the connector. A connector Derive hidden connections (below) created elsewhere — on a different view — is marked internally as "derived," and is skipped by this connector pull-in UNLESS Include existing derived connectors (off by default, right below Missing connectors) is checked — so a connector implied for one view doesn't silently spread onto every other view that happens to already show both its endpoints. A third option, Auto-complete streams in model, instead finds every stream name already tagged on a part in the current model and checks each one against a chosen stream template — it shows a review list of every missing (stream, type, label) position with checkboxes for Part and View (a node can't be created without its part, so unchecking Part also unchecks and disables View); nothing is created until you click Proceed. Both this and Smart Check Node are also Composition-aware: if the current view was created by Level Down, a connector added to the parent-level part afterward shows up here automatically (connected to this view's own anchor, not the parent — the parent itself is never duplicated as a node), and a connector you add here to something outside this decomposition is mirrored back up to the parent for its own next Smart Check run. A connection to a sibling under the same parent stays purely internal and isn't mirrored. A fourth option, Sync existing connectors with inventory (off by default), compares every connector already on the view (or, for Smart Check Node, touching that one node) against its related part-to-part "inventory" connector — e.g. Level Down's own original crossing connector, or one Smart Check itself created — and updates the view's copy to match wherever they differ. This only runs when checked; nothing about relationship/type/streams is kept in sync automatically otherwise. To push a change the OTHER way — from a view connector back up to its inventory connector — see the prompt described under Property Panels below. A fifth option, Derive hidden connections (off by default; uses the same Levels setting as the second option, above), runs last: for any two nodes already on this view that are only linked through a chain of one or more parts NOT on this view, it adds a real Connector directly between them — the same "derived" concept Insert Smart Stream uses (see above), creating both a Connector ('c') and a Stream ('s') version and noting which off-view type(s) it stands in for. Since it runs after the other options' own additions, a node that Missing connectors and nodes just pulled in this same run no longer counts as "hidden" and won't get bridged. Every connector it creates is flagged internally as derived — see Include existing derived connectors, above.
Smart Check Node(Advanced menu, or right-click a single node) The single-node version of Smart Check View — same "missing connectors" / "missing connectors and nodes, N levels" idea (including the same Composition-awareness described above), but starting from just the node you right-clicked instead of the whole view. Two extra options this scope adds: Upstream/Downstream (which direction to follow connectors relative to that node), and By Stream (only follow connectors tagged with the node's own stream(s) — pick one or more if it has several). The stream filter stays fixed to whatever you picked from the original node: if a node it pulls in turns out to also carry some other stream, that other stream is not used to keep expanding the search.
Generate Industry / Generate Inventory View(Advanced menu) Bulk-generate a starter set of parts/connectors from the currently-loaded industry data, or a summary inventory view of everything in the model. Only one industry dataset is ever loaded at a time — DyCAD starts with a built-in default; File > Load SFCCE replaces it (warning first if something's already loaded, since this can't be undone by re-picking a name — there isn't one) with a Section/Function/Capability/Application Capability/Entity collection read from an arbitrary JSON file (with a field-mapping step, since the shape can be anything, including nested groups of groups). Whatever's currently loaded is saved as part of your document, so it survives Save/Load JSON. Capability, Application Capability, and Entity are all optional: leaving one unmapped means it simply inherits the name of the level above it, rather than being dropped — so the same wizard handles data with only a single capability concept just as well as data with a distinct Business/Application Capability split. A Domain that ends up spanning more than one Section (its own Business Capabilities/Application Capabilities combined together) can be collapsed into one shared Domain or kept as separate numbered copies — the one "combine into shared?" question the wizard asks (a Business Capability or Application Capability that happens to span sections independently of its own Domain is folded into whichever choice its Domain got, automatically, no separate question). A collapsed shared Domain lands under the real Section chosen in the mapping dialog's own "Section for shared functions" selector (defaults to Centralized Operational Functions), not a placeholder "Shared" tag. Review the result via Catalogs > SFCCE before generating. Every part a Section's Function generates (capability, application capability, entity, and any supporting nodes) inherits that same Section, so the Section filter shows the whole related chain, not just the Function itself. Each distinct Section also gets its own Business Organization Unit node generated (reused, not duplicated, across every Function that shares it), Assignment-connected to the Function(s) it's responsible for — a real, visible node representing the section itself, not just a filterable tag. Every level (Section, Function, Capability, Application Capability, Entity) can also optionally map a Description field and an Id field — an unmapped Id falls back to an auto-generated one, while a mapped Id gives that node a real, stable identity (so re-generating later reuses it instead of creating a duplicate). Unlike names, Ids never inherit from the level above when left unmapped. An Id field also offers (generate unique) — mints a genuinely fresh, random id instead of reading anything from the file at all. The mapped Section Id/Description also show up directly on the generated Business Organization Unit node's own properties (previously always empty), and in the Catalogs > SFCCE table. Right-click the Load button to copy the exact mapping as a ready-to-paste function call, the same shortcut Remap's own submit button offers.

AI-Assisted Capability Data Generation

No suitable industry data on hand for Generate Industry or File > Load SFCCE? Paste one of these prompts into an AI assistant to produce a JSON file in the right shape. Neither prompt is DyCAD-specific — the AI just needs to follow the JSON shape described; any assistant capable of following structured instructions and producing valid JSON will do.

GoA_Capabilities_to_SFCCE — condenses a flat list of fine-grained capabilities (each tagged with the ministries/departments that rely on it) into a smaller set of broader business capabilities, each still listing its own original fine-grained capabilities underneath. Use this when you already have a flat capability inventory and want it organized into DyCAD's two-tier Capability/Application Capability shape.

You will receive a JSON file shaped as an array of domains, each with a flat list of
fine-grained "application capabilities":
  [{ "domain": string, "capabilities": [{ "name": string, "description": string,
     "ministries": string[] }, ...] }, ...]
(Other fields on each capability, like repo_count, can be ignored and dropped.)

For each domain, group its application capabilities into a smaller number of
broader, outcome-oriented "business capabilities" -- capabilities describing WHAT
the business does, not the granular systems/features that support it. Every
application capability must end up under exactly one business capability, none may
be dropped, merged away, or renamed. Business capability names/descriptions are new
and yours to write (aim for roughly 5-15 application capabilities per business
capability, fewer for small domains); the application capability's own
name/description/ministries must be copied through unchanged.

Output ONLY a JSON array in this exact shape, one entry per input domain:
  [{ "domain": string,
     "businessCapabilities": [{ "name": string, "description": string,
       "applicationCapabilities": [{ "name": string, "description": string,
         "ministries": string[] }, ...] }, ...] }, ...]

Save the result as capabilities_merged.json.

Industry_to_SFCCE — generates a capability map for an industry from scratch, no source file needed. Fill in the {{INDUSTRY}} placeholder before running it. Every Function also carries its own description and id, and a fixed baseline of ~29 generic enterprise-support Functions (Accounting, Audit, Procurement, Human Resourcing, and so on) is included verbatim, matching DyCAD's own built-in Populate From Template > Enterprise Functions template — a generated file's Functions line up with that template's own functionId/Section assignments out of the box. Sections are listed per Application Capability, not per Function — an Application Capability can (and often does) span several Sections, which the wizard's own shared-Section detection step handles on import. Entities are the concrete data records/objects a Capability or Application Capability manages — e.g. "Sales Order," "Customer Profile," "Bill of Materials," the same kind you'll see if you look at DyCAD's own built-in default industry dataset (Catalogs > SFCCE) — not systems, processes, or documents.

Generate a capability map for the {{INDUSTRY}} industry, suitable for import into
DyCAD via File > Load SFCCE.

Structure it as a JSON array of top-level business Functions, each with a description
and its Business Capabilities; each Business Capability contains Application
Capabilities. Each Application Capability is tagged with the Section(s) -- business
units, departments, or lines of business -- that rely on it, and lists the concrete
data Entities it manages (records or objects like "Sales Order" or "Customer Profile,"
not systems or processes):

  [{ "function": string, "functionDescription": string, "functionId": string,
     "businessCapabilities": [{ "name": string, "description": string,
       "applicationCapabilities": [{ "name": string, "description": string,
         "sections": string[], "sectionId": string,
         "entities": [{ "name": string, "description": string }, ...] }, ...] }, ...] }, ...]

Cover the industry's full breadth -- as many Functions, Business Capabilities,
Application Capabilities, and Entities as genuinely apply, with no target count or
upper limit. Every name should be specific to {{INDUSTRY}}, not generic boilerplate
(the baseline Functions below are the one deliberate exception -- include them as-is).
Descriptions are one concise sentence. "sections" should list every realistic
organizational unit that relies on an Application Capability -- reusing the same
section names across many entries is expected and normal, and a capability spanning
several sections should list all of them, not just one.

Prefer reusing one of these known Sections by name wherever it genuinely fits, but
they are not a closed set -- add industry-specific sections freely wherever the
known ones don't apply:

  Centralized Operational Functions (Economies of Scale), Continuous Improvement
  Functions, Enterprise Scope Functions, Finance Control Functions, Mainstream
  Operational Functions, Resources Sustainment Functions, Staff Specialist Functions

What each Section means:

  Enterprise Scope Functions -- Functions at CEO/COO level encompassing the whole
  organization.
  Mainstream Operational Functions -- Customer-focused Functions meeting the needs
  that define what the organization is about. Organized into Core Programs; each
  Function can be delivered through a corporate service (e.g. procurement) or within
  its own program.
  Staff Specialist Functions -- Functions assisting operational managers in the major
  dimensions of their work.
  Continuous Improvement Functions -- Functions addressing improving any other
  Function.
  Resources Sustainment Functions -- Functions concerned with ensuring that human,
  financial, capital, and technical resources are well maintained and not allowed to
  deteriorate.
  Finance Control Functions -- Functions that measure/control resources within the

4. Filtering, Streams & Catalogs

Every control below only appears in the toolbar while the current tab is one it actually applies to — e.g. View Scope/Connector Type/Layer Order/Highlight only show up on a 3D View tab, Levels only on a canvas tab, and none of them show up at all on a catalog table or other non-diagram tab — rather than sitting there disabled and confusing.

  • View Scope (3D View only) — narrows the whole scene down to exactly what one chosen 2D view has placed (its own parts AND connectors), instead of the whole document. "All (whole document)" is the default.
  • Stream filter — show only nodes/connectors tagged with a chosen stream; select-all/ exclude-all and scrollable for models with many streams.
  • Type filter — show only chosen element types; select-all/exclude-all and scrollable for toolkits with many types.
  • Section filter — show only parts tagged with a chosen Section (the plain text field, not a Section-view's own structural grid); a part with no section at all is offered as its own "(no section)" option. Same select-all/exclude-all as Stream and Type.
  • Connector levels — when a Stream, Type, or Section filter is active, how many extra hops of connected nodes to also show beyond the ones that directly match (blank = unlimited). Lets you see a filtered node's immediate context instead of it floating in isolation.
  • Connector Type filter (3D View only) — which connectorType(s) draw at all: 'c' Connectors and/or 's' Streams. Same select-all/exclude-all pattern as Stream/Type/Section. Disabled on a canvas tab, where this is instead a per-view setting (Show Connector Type / Show Stream Type).
  • Highlight (3D View only) — NOT a filter: draws a wireframe box around every part of whichever checked element type(s), while everything else keeps rendering normally. Useful for making one or two types of interest visually pop out of a large scene (e.g. every Business Function) without hiding anything else.
  • Toolkit filters (left sidebar) — Source chips (TOGAF/ArchiMate/Other) and Group chips (Application/Business/Data/etc., shown in light blue) narrow which element types appear in the drag-and-drop toolkit itself.
  • Catalog tables — Parts, Connectors, Views, and ViewMembers each have a full sortable table, independent of any one diagram — useful for bulk review or finding something by name rather than hunting across views. Selecting a row shows the same property panel a canvas selection would. Click a column header to sort by just that column; shift+click another header to add it as a secondary sort (e.g. click "Type" then shift+click "Label" to sort by type, then by label within each type) — each active column shows its rank (①②③...) and direction. Shift+click an already-active column again to flip just its own direction; a plain click on any column resets back to a single-column sort. The same multi-column sort works in the SFCCE preview table (Catalogs > SFCE) too.

Explore > 3D View — a rotatable/zoomable 3D scene over your Parts and Connectors directly, covering the whole document by default (not any one 2D view's placement of them) — unless you narrow it with the View Scope selector (top toolbar, 3D-only): pick a specific view there and the scene shows exactly what that view has placed (its own parts AND connectors), the same content you'd see looking at it in 2D, instead of everything in the document. Pick "All (whole document)" to go back to the default. Parts are grouped into layers by element type, stacked into broader bands by element group, colored the same as the toolbox/canvas; within a layer, parts cluster into their own band by Section, then by Stream. Each (Section, Stream) band reserves the SAME row across every element type's layer, not just within its own — so a given Section/Stream's parts line up at the same height whether they're a Business Function or a Data Entity, keeping the connectors between adjacent layers (the main dependency chain) far less tangled than if each layer packed its own grid independently. Each Section's own cluster within a type's layer gets a visible boundary outline and a floating text label with its name, always facing you as you rotate. Connector lines are drawn between Parts the same way they'd be hidden on the 2D canvas — a connector only shows once both its ends are visible — and are styled per relationship the same way the 2D canvas is: each relationship's own color, dashed-vs-solid line, and a small direction marker (a cone, an elongated diamond, or a sphere, approximating that relationship's 2D line-end shape) at whichever end(s) it points — e.g. an arrow cone into the "to" end for most relationships, a diamond at the "from" end for Composition/Aggregation. The Stream, Type, Section, and Connector Type filters (top toolbar) all work here too, narrowing which parts (and their connectors, and their section boundaries) appear — Connector Type is 3D-only, since it chooses which connectorType(s) ('c' Connectors, 's' Streams) draw at all, a concept the 2D canvas instead controls per-view. The Layer Order selector (top toolbar, 3D-only) picks which streamTemplate decides both layer sequence AND which element types show up at all — independent of whichever template Remap/Generate Stream last used, since this is a separate concern from generating a stream. Defaults to All, a built-in template covering every known element type in a fixed reference order (so nothing is hidden by default); picking any other real template (e.g. "Enterprise") narrows the WHOLE scene down to just the types that template actually cares about — its main value[] chain plus any type its passive relationships (e.g. Enterprise's Business Function, tied to Business Process) mention — anything neither list touches doesn't render at all, not just falls to the back of the order. The Highlight picker (top toolbar, 3D-only) draws a bright cyan wireframe box around every part of whichever element type(s) you check — e.g. check "Business Function" to make every Business Function part visually pop out from the rest. Purely a visual call-out, not a filter: unlike Type, an unchecked type's parts stay exactly as visible as before, and checking more types adds to the highlight rather than replacing it. Click a part to focus it (a yellow outline highlights it) and show its properties in the panel on the right, with the same controls as selecting it in a 2D view. Zoom in further while it's focused and you'll jump straight to a 2D view that already has it placed, with that part selected there — or double-click a part to jump immediately, skipping the zoom. A part not yet placed on any view just keeps showing its properties instead of jumping anywhere. Clicking a part never moves the camera — it highlights in place, so rotating/zooming afterward still pivots around wherever you were already looking. Once you've stepped or run a simulation, every part with a live value gets a small colored marker floating above it — green for normal, blue (pulsing) for one that just changed this tick, red for one that errored — the same colors the 2D canvas's simulation badges use, so results read the same way in both places. It shows the current tick only, not a history you can scrub back through. Right-click a part for a quick menu: filter to just one of that part's own Streams (each stream it carries gets its own item — picking one switches to just that one rather than combining them; pick "All of the above" to filter to every stream the part carries at once, like before). Right-click and drag a part instead to move it anywhere in 3D space — dropping it "pins" it there (saved with the document), and it's excluded from the auto-layout grid entirely from then on, so it won't shift when other parts are added/removed. A dragged part doesn't also open the quick menu. Pin as many parts as you like, then Explore > Reset Pinned 3D Positions to unpin all of them at once and let auto-layout take back over (there's no per-part unpin — it's an all-or-nothing reset). Panning uses middle-click-drag here (right-click is reserved for the menu/drag instead).

5. Property Panels

Selecting a node or connector on canvas shows two layers, deliberately kept separate:

  • Top level — fields that belong to this view's placement of the part/connector: position, Fill Color, Order, whether it's flagged External, and (for connectors) which nodes it connects on this view.
  • Root Properties (collapsible section below) — fields that belong to the underlying part/connector itself, shared across every view: Label, Type, Description, Script, Note, Relationship, and the read-only Created/Updated timestamps. Editing something here changes it everywhere that part or connector appears, not just on this view.

The same split applies to the Parts/Connectors catalog tables, which show only the Root Properties side (there's no "view placement" to speak of when you're not looking at a specific diagram).

Changing a connector's Relationship or Streams — whether from Root Properties or the quick relationship picker you get by clicking a connector on canvas — also checks whether that connector has a related part-to-part "inventory" connector elsewhere in the model (see Level Down and Smart Check View's own Composition-awareness, above). If it does, you're asked whether to update that inventory connector to match too. Say yes to keep both in sync; say no to let them intentionally diverge. Most connectors have no such counterpart and are edited with no extra prompt at all.

A few fields exist in the panel but currently have no visible effect — Font Color, Font Size, and Border Color on a node, and Margin on a view. They're stored if you set them, but nothing in the current build reads them back to change how anything looks. Worth knowing so you don't spend time tuning a setting that isn't wired up yet.

6. Simulation Scripting

Any part can carry a script that runs once per simulation "tick," letting you model how values or state flow and change across a live architecture — not just a static diagram. Turn it on per-part with "Part Script Enabled" in Root Properties, then write the script body in the Script field.

What a script receives (the ctx object)

FieldWhat it is
ctx.partThe part record itself (id, type, label, ...).
ctx.inputsOne entry per incoming connector this tick: { fromPartId, fromLabel, connector: { relationship, streams }, value }. A neighbor that hasn't produced a value yet shows value: undefined.
ctx.responsesOne entry per outgoing connector whose target sent a response back last tick (same shape as inputs) — see "Responses" below.
ctx.stateWhatever this part's own script returned as state last tick — empty on tick 0 or right after Reset. This is how a script remembers something between ticks.
ctx.tickThe current tick number, starting at 0.
ctx.log(message)Writes a line to the Message Log panel — use freely for narration or debugging while building a script.
ctx.secretsRead-only access to your Local Secrets (File > Load Local Secrets — e.g. an API key) that should never end up saved into a shared model file. Deliberately memory-only — never cached to localStorage either, so it must be re-loaded each browser session, unlike File > Load/Save Local Settings (pinned fields, Max Script Entities, node size, the Script Console's own text, and Insert Smart Stream's and Remap's saved presets) which IS cached and auto-applies on startup.
ctx.setState(patch)For asynchronous work (e.g. a fetch whose result arrives later) — merges into this part's state at the start of the next tick rather than immediately.
ctx.loadedFileNameThe filename of the last file that fully replaced the model (Load JSON / File > Load / File > Load Example) — null if nothing's been loaded that way yet this session. Not set by Import Data, which merges rather than replaces.
ctx.currentViewThe view id currently shown in the main view selector, as of the moment this tick started.
ctx.defaultModelThe model new parts/connectors get created into by default — not necessarily the same as ctx.part.model (a part can live in any model).
ctx.findParts({ type, model })Read-only lookup across the whole document, not just this part's own inputs/graph — returns every Part matching the given type and/or model (both optional). e.g. ctx.findParts({ type: 'BusinessCapability', model: ctx.part.model }) to list every capability in this part's own model. Treat the result as read-only.
ctx.createPart({ type, label, model, ... })Creates and returns a brand-new Part. model defaults to ctx.part.model if omitted — pass a different model string to create in a different model. The new part takes effect starting the next tick, same "one tick later" rule as response; it isn't placed on any view automatically. Throws if type is missing, or if the parts+connectors cap would be exceeded (see below).
ctx.createConnector({ from, to, model, connectorType, relationship, ... }) Creates and returns a brand-new Connector between two existing part ids. model defaults to ctx.part.model if omitted. Throws if from/to don't resolve to real parts, or the cap below would be exceeded.
ctx.createNode({ objectId, view, x, y, fillColor, note, order }) Places an existing Part (from createPart, findParts, or a known id) onto a view as a visible node — a Part on its own has no viewMember, so it never shows up on any canvas until something places it. view defaults to ctx.currentView if omitted; throws if neither resolves to a real view. Find-or-create: calling it again for a part already placed on that view returns the existing node unchanged rather than adding a duplicate, so it's safe to call every tick. x/y are a desired position only (default 0,0) — placed via the same overlap-avoiding search every other placement path in the app uses, and ignored on a section-based view, which places into its own grid instead. Doesn't create connector edges — use createConnector for the relationship itself, and createNodeConnector to show it on a view.
ctx.createNodeConnector({ objectId, view, note, order }) Places an existing Connector (from createConnector or a known id) onto a view as a visible edge between its two endpoint parts' current nodes there — a Connector on its own has no viewMember, so it never draws a line until something places it. view defaults to ctx.currentView if omitted, same as createNode. Both endpoint parts must already have a node on that view (place them first with createNode) — throws naming whichever endpoint is missing one rather than guessing or skipping it. Find-or-create: returns the existing edge unchanged if this connector already has one on this view.

ctx.createPart/ctx.createConnector are capped by Max Script Entities (default 5000) — the total parts.length + connectors.length a script is allowed to grow the document to. Hitting the cap throws an error (same as any other script error, visible on that node) rather than silently doing nothing — a script that creates something every tick with no guard will hit it fast under continuous Run. Configurable via File > Load Local Settings, which caches it to this browser's localStorage so it stays in effect across page refreshes without re-loading the file. The same file/mechanism also holds the node size multiplier — see Views & Layout above.

It has full app/store access (more powerful than a part's sandboxed ctx, since it's an explicit tool a person runs, not something a saved document executes unattended). Its own dialog splits into a Console tab (output + editor, open by default) and a Reference tab (the bindings/options table below) — switch to Reference when you need to look something up; Console stays the wider, taller default view. A script builds its own tab when it needs one, e.g. via app.createCanvasTab(view) / app.switchToTab(tab.id).

The editor's text is a real script FILE, not a one-off REPL entry: it's saved as you go (both to this browser's localStorage and, if you edit it, alongside File > Save Local Settings — see below), and Run doesn't clear it afterward. Run (or Ctrl+Enter) defines everything currently in the box — so any function foo() {...} you write becomes callable — then calls whichever function is selected in the "Function" dropdown next to the Run button, which is free to call whatever other functions you've defined alongside it (they all share the same bindings automatically, without needing them passed in). That dropdown lists every top-level function in the script, sorted alphabetically, and refreshes as you type; it defaults to main() when present, and otherwise remembers your last selection across edits where possible. The default script's main() runs five starter batch scripts in sequence — the convention for adding your own is BatchScript_<Name>, with main() picking which one(s) to run, in whatever order. First, BatchScript_QuickStart() builds the "Business Functions" view end to end, ending with the 3D View. Then BatchScript_InsertSmartStreamExample() runs — a full insertSmartStream call (Streams, both directions, starting from a Business Function named "Production" out to Data Entity, several element types shown) against the very data BatchScript_QuickStart just generated, landing on a new "Smart Stream Example" view. It's the same trace as the "StreamSet1" preset that ships with the Insert Smart Stream dialog (see Commands above) — one usable both as a script and as a ready-made dialog preset. Next BatchScript_SmartCheckViewExample() runs Smart Check View on that same view with Missing connectors and Derive hidden connections checked. Then BatchScript_RemapExample() remaps that same "Smart Stream Example" view using the Layered pattern (both Minimize Crossings and Minimize Connector Length enabled, no Edge Assignment needed — Business Function and General Actor land on the top row for free, as true graph roots) — these first four steps all reuse the same tab rather than opening a new one. Finally BatchScript_InsertSmartStreamExample2() runs the same trace again with a broader set of element types shown, but always builds its own separate "Smart Stream Example 2" view (never topping up the first one), ending as the active tab; main() logs a reminder to the Message Log naming the exact Smart Check View/Remap settings to run on that second view yourself, rather than running them automatically.

Not every function in the script is meant to be reached through main(), though — the default script also defines dataAutoFill(), which Data Modeling > Autofill (see above) calls directly by name instead, since it only makes sense to run against a view that already has Data Entity Details tables on it. Editing dataAutoFill() here changes what that menu item does.

A third kind of function belongs here too: anything meant to be called from a part's own script (see "Node Scripting / Simulation" below), not from main() or a menu item. Every function/const defined anywhere in this Script Console text is automatically in scope inside every part script — a part's script can call it by name, using its own ctx. The default script ships one ready-made example, CommonScript_Example(ctx), which logs "called by <type> <label> <model>" to the Message Log using the CALLING part's own ctx.part — a part's script just needs a line like CommonScript_Example(ctx);. The convention for adding your own is CommonScript_<Name>, kept visually distinct from BatchScript_<Name> (main()) and dataAutoFill (Autofill). A common function you write this way can use anything its own ctx parameter provides — it has no access to app/store directly, the same restriction any part script already has.

A fourth kind of function belongs here too: a user-designed Remap layout (see "Remap" above), picked interactively from that dialog's Pattern dropdown ("Custom" reveals a second dropdown listing every matching function found here) rather than called from main(), a menu item, or a part script. The convention is CustomRemap_<Name>(ctx); the default script ships CustomRemap_Example, which groups a view's parts onto one row per element type using grid coordinates. See "Remap" above for what its own ctx provides.

Code Summary

Advanced > Code Summary opens a read-only listing of the Script Console's own text plus every part's own script in the current document, for security review before running an unfamiliar simulation or batch script (both run with full access to the document — creating parts/connectors, calling findParts — and to any configured API secrets). Every part with a script is listed regardless of whether its "Part Script Enabled" checkbox is currently on, since a disabled script could always be re-enabled later; each entry is clearly marked ENABLED or disabled and identifies its source part by label, type, and id, grouped by model.

What a script must return

A script must return an object { value, state, response, badge } — response and badge are both optional.

  • value — what downstream connectors carry to their targets next tick.
  • state — carried forward to this same part's own ctx.state next tick.
  • response (optional) — a value sent backward to every node that feeds into this one, arriving as their ctx.responses one tick later. Useful for acknowledgement/feedback flows where a downstream node needs to signal something back upstream.
  • badge (optional) — { text, color } to show a freeform label on the node (bottom-right), independent of the automatic value badge. Only shows while the view's "Show Right Badge" toggle (Filters panel) is on, and only for the tick a script actually returns one.

A minimal example

// Adds up every incoming value and passes the sum onward.
let sum = 0;
for (const input of ctx.inputs) {
  if (typeof input.value === 'number') sum += input.value;
}
return { value: sum, state: {} };

A part with no script (or script disabled) just passes a single input through unchanged if it has exactly one incoming connector, otherwise sits idle. A thrown error is caught per-part — that node keeps its last good value, the error is logged, and every other part still runs normally that tick.

Simulation runs per Model, not per view, using every scripted part in that model regardless of which views currently show them — use the model selector next to the simulation Run/Pause/Step/Stop controls to choose which one you're running.

7. ArchiMate Import

Import a standard ArchiMate 3.0 Exchange Format file (File menu) to bring in its elements, relationships, and views as DyCAD parts/connectors/views. Notes on how it handles two ArchiMate conventions that don't map directly onto DyCAD's own model:

  • Junctions (AND/OR routing points) aren't imported as nodes — DyCAD has no equivalent. Instead, each junction is dissolved: every real source connects directly to every real target it fed through the junction, with a note recording which logic (AND/OR) the junction used to represent.
  • Nested shapes — some ArchiMate diagrams show a Composition or Aggregation relationship by drawing one shape inside another instead of a connecting line. DyCAD detects this and adds the connector anyway, noting on whichever record it had to create ("connector" if the relationship didn't exist yet, otherwise the view placement) that it was inferred from nesting rather than an explicit line.

Re-importing the same file is safe — it matches existing records by the file's own stable ids and updates them in place rather than duplicating.

7a. Data Modeling

The Data Modeling menu adds entity-relationship (ERD) detail — typed attributes, primary/ foreign keys, and crow's-foot notation — on top of the Data Model's existing Data Entity element, without changing what a Data Entity already means elsewhere in your model (Streams, Capability Maps, etc. all keep working exactly as before).

Add/Edit Entity Details

Select a single Data Entity node and choose Data Modeling > Add/Edit Entity Details — this is the same "level down" mechanism used elsewhere in the app (double-clicking a node to open its own detail view), just triggered from the menu. The first time, it creates a new Data Entity Details node on its own view, linked back to the Data Entity via a structural Composition connector. Running it again on the SAME Data Entity — even from a different view, if that Data Entity appears in more than one place — reopens the existing Entity Details rather than creating a second, disconnected one.

The reverse direction works too: select a single Data Entity Details node and run Level Up (Commands toolbar or right-click) — the first time, it creates a new Data Entity node of the same name on its own new view, linked back down to this Entity Details view the same way Add/Edit Entity Details links down from the Data Entity side. Running Level Up again on the same Entity Details node reopens that existing Data Entity instead of creating another one.

A Data Entity Details node has its own Attributes table in the property panel: click + Add Attribute for a new row, fill in Name and pick a Data Type from the dropdown (numeric, string, boolean, date, blob, json — if an attribute already has some other value, e.g. a concrete SQL type brought in via DDL import, that value stays available as an extra option so it's never silently overwritten), and check Null/PK as needed. Tab moves you through each row in order — Name, Data Type, Null, PK, then the next row's Name — so you can key in a whole table's attributes without touching the mouse. The ▲/▼ buttons on each row reorder attributes. The same attribute list also shows directly on the node itself on the canvas (name : data type, 🔑 for primary key) — toggle it per-view with the Attributes checkbox next to Description/Types in the view's own properties, same as any other node-content toggle. A "FK" badge appears automatically, both on the node and in the panel, on whichever end of a Data connector's From/To Attribute pair points at the OTHER end's Primary Key — it's computed live from your actual connectors and their attributes' PK flags, not something you set yourself (there is no "Is Foreign Key" field to check — setting one by hand does nothing), so it can never get out of sync with what's really connected.

Autofill

Data Modeling > Autofill scaffolds a whole view's worth of tables and relationships in one click. For every Data Entity Details node on the current view that doesn't have any attributes yet, it creates three: <label>Id (numeric, primary key), <label>Name and <label>Description (both string, nullable) — a table that already has even one attribute is left completely untouched, never merged with or topped up. Then, for every Data connector on the view whose From Attribute isn't set yet, it wires From to the source table's own primary key and To to a same-named attribute on the target table (created if it doesn't already exist there), with cardinality set to One (from) / One or Many (to) — a connector that already has its From Attribute set is left alone.

Autofill isn't a hidden built-in command — it runs a real, editable script called dataAutoFill() that lives in the same place as the Script Console's own example scripts (Advanced > Script Console; see the BatchScript_QuickStart example there). Open the console to see or change exactly what Autofill does — anything you edit there takes effect the next time you run Autofill from the menu.

Crow's-foot relationships

Drag from one Data Entity Details node to another (the small handle at its bottom-right corner) the same way you'd draw any connector — between two Data Entity Details nodes this automatically creates a crow's-foot (Connector Type: Data (d)) relationship instead of a plain one, no extra step needed. If the table you dragged FROM has a primary key attribute, a matching foreign key attribute is created automatically on the table you dragged TO (named after the source table and its primary key, reusing an existing attribute of the same name instead of duplicating it if one's already there), and From/To Cardinality are set to One/Many automatically. Its property panel exposes four fields: From/To Attribute (pick which column on each table the relationship actually connects — the dropdown only offers that table's own attributes; this is also how you set a foreign key manually, since FK status is derived from here) and From/To Cardinality (One, Many, Zero or One, One or Many), which control which crow's-foot symbol is drawn at each end — free to change after the fact if the auto-populated One/Many isn't what you meant.

Connector Type is a regular editable field on every connector (not just Data ones) — so if you drew an ordinary connector and want to turn it into a crow's-foot relationship instead (or the other way around), just change its Connector Type in the property panel directly.

Import/Export DDL

Import DDL... reads a .sql file's CREATE TABLE statements (a common subset — column definitions, inline or table-level PRIMARY KEY, table-level FOREIGN KEY ... REFERENCES — not every SQL dialect's full syntax) and builds one Data Entity Details node per table, with Data connectors for every foreign key, on a new view. If anything in the file falls outside that subset, nothing is imported and you'll see exactly which table/line caused the problem. Export DDL generates DDL text back from whatever Data Entity Details nodes and Data connectors are on the current view (not the whole model) and shows it in a read-only text box you can select and copy from.

Auto-Detect Connectors

Data Modeling > Auto-Detect Connectors... scans every Data Entity Details table in the whole model (not just the current view) for likely relationships that aren't connected yet, and shows you a preview list to check over before anything is actually created — nothing happens until you click Create Selected Connectors. It combines two ways of finding candidates:

  • Paste DDL text containing FOREIGN KEY ... REFERENCES clauses into the box at the top (this is optional) — each one is matched against tables/columns that already exist in your model. This is the same explicit signal Import DDL uses, just matched against existing tables instead of creating new ones.
  • Whether or not you paste anything, a field-name match always runs too: any non-primary-key attribute whose name matches another table's primary key — either exactly (e.g. both called "Code") or by the common "<Table>Id" convention (e.g. Customer's primary key "Id" matching an Order attribute named "CustomerId") — is proposed as a likely one-to-many/foreign-key relationship.

Every candidate starts checked; uncheck any you don't want before confirming. A pair already connected by an existing Data connector is never proposed again. If both tables in a confirmed pair already share a view, the new connector is placed there automatically; if they don't share any view yet, the connector is still created (so it's ready once you do place them together) but won't be visible on any diagram until then.

8. Tips & Things to Know

  • Undo/Redo (Ctrl+Z / Ctrl+Shift+Z) covers the full model, not just the current view — it's safe even though views share underlying parts and connectors.
  • The Message Log (left sidebar) records every warning/rejection message the app shows you, not just the ones you happened to catch as a popup — worth checking after a bulk operation (Smart Check View, a big drag-and-drop, an import) to see everything that happened, with Copy and Clear buttons for convenience.
  • Rejections give a specific reason — e.g. dragging a node into a section that doesn't allow its type names the section and what it does allow, rather than a generic "that didn't work."
  • A part's Note and a view's Margin are stored but not currently shown anywhere on the canvas itself (Note does appear in the catalog table and the row's Copy text) — don't expect a visual change from editing them.
  • Everything nested-shape or junction-related is a permanent tradeoff, not a bug to chase — force-directed layout can't guarantee every edge in a cycle lands in an adjacent cell (a hard 2D-layout limit, not a DyCAD gap), and obstacle-avoiding routing only looks at nearby obstacles for performance reasons on large diagrams.
