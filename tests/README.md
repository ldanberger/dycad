# DyCAD regression suite

A lightweight Playwright-based regression net covering the mechanisms that have
actually broken during development — not exhaustive feature coverage, but the specific
things that are easy to silently break while changing something else nearby.

## Running

```
cd dycad
python3 tests/run_all.py
```

Requires `playwright` (`pip install playwright && playwright install chromium`). The
script starts its own local server on port 8123, runs every check against a fresh page
each, and prints a PASS/FAIL line per check with a short detail message. Exits non-zero
if anything failed.

## What's covered, and why each check exists

|---|---|
| `check_boots_clean` | Any change breaking the app at load time |
| `check_example_simulates` | The bundled example / simulation engine breaking |
| `check_sim_snapshot_rejects_pre_rebrand_tag` | A deliberate behavior change, reported directly: "update documentation, remove all reference to flowrun" (confirmed explicitly that this should extend to dropping `loadSimSnapshot`'s pre-rebrand compat path, since the project has no prior users to keep backward-compatible). `loadSimSnapshot` used to accept either `'dycad-sim-snapshot'` or the pre-rebrand `'flowrun-sim-snapshot'` as a valid snapshot `kind` tag; now only the current tag is accepted, with the old one rejected exactly like any other unrecognized file. Covers both directions — the old-tagged file is rejected (specific toast, no `simRuntime` entry created) and the current-tagged file still loads correctly (real `simRuntime` entry, success toast) — so the check fails specifically if the compat path is silently reintroduced, not just if snapshot loading breaks in general |
| `check_remap_patterns` | Any of the four Remap patterns (default/none/layered/force) throwing |
| `check_remap_layered_pattern` | `computeLayerAssignment`'s row-by-graph-hop-distance rule (pattern:'layered') using longest-path/topological-sort layering instead of shortest-path — a node reachable from a root by both a short direct edge AND a longer indirect one must land on the row its NEAREST dependency justifies, not be pushed down by the longer path (this is what merges Business Capability and Business Process onto one row for the real "Smart Stream Example" data); a genuine 2-node cycle (DyCAD's dual-connector convention) throwing or hanging instead of BFS's "already visited" check naturally no-op'ing the back edge; Edge Assignment/Minimize Crossings/Minimize Connector Length breaking when combined with pattern:'layered' |
| `check_remap_crossing_minimization_finds_global_optimum` | `minimizeRowCrossings` (shared by default/none/layered) converging to an ordering that's tied with a better one on raw crossing count and never preferring the better tie — specifically Business Function left at one end of its row instead of centered between its two Processes, and Business Capability/Business Process (a same-row pair under pattern:'layered') left "grouped" apart instead of interleaved adjacent to their own Process/Capability. Runs on the EXACT real "Smart Stream Example" topology and BatchScript_RemapExample's own sortKeys (a smaller synthetic 2-/3-row fixture tried first did NOT reproduce the bug — confirmed via testing that the failure only shows up once a row is pulled from both above and below simultaneously) |
| `check_remap_layered_avoids_node_occlusion` | Direct follow-up: "smart stream example from script console is directly placing nodes over connectors instead of resizing to fit properly after remap. why? what remap settings are needed to avoid this?" — then "yes, treat it as a real penalty in the scoring." `minimizeRowCrossings`'s crossings-first scoring could lock in a same-row column order (Process, Process, Capability, Capability) that's genuinely better on cross-row crossings than the interleaved alternative, even though the same-row Capability→Process connector then draws a straight line directly through the OTHER pair's Process node sitting between them — a defect no existing Remap setting (Minimize Crossings, Minimize Connector Length, Edge Assignment, Spacing Scale) could avoid. Runs the REAL generateIndustry → insertSmartStream → smartCheckView → applyRemapLayout pipeline (not the sibling check's synthetic fixture, which doesn't reproduce this — its extra connectors already score the interleaved order best on crossings alone) with BatchScript_RemapExample's own exact options, then checks EVERY connector's straight-line path against EVERY other node's bounding box for genuine intersection, proven via TEMP BREAK to reproduce all 4 real overlaps before the new `occlusions` criterion existed |
| `check_custom_remap_grid_convenience_layer` | New-feature check for the 'custom' Remap pattern, from a short design back-and-forth: "is it possible to build a small framework for user designed remap logic, something that can be loaded in and stored in user local settings perhaps" → "can there be an option to use grid coordinates based on rows and columns and spacers between, as an alternate to the x,y canvas coordinates?" → "yes go with the convenience layer at remap time. please build it." ## Fixtures

`fixtures/mini_archimate.xml` — a minimal ArchiMate 3.0 Exchange Format file, hand-built
specifically for this suite (not derived from any user file), containing:
- A→Junction→B via an AndJunction, to exercise junction flattening + bypass placement.
- A Composition relationship between "Whole" and "Part" represented by nesting "Part"'s
  diagram node inside "Whole"'s, with no explicit `<connection>` element, to exercise
  nested-shape detection.

This is deliberately small and synthetic. It's a fast, stable regression guard for the
*mechanism* — it is not a substitute for testing against a real, complex ArchiMate
export when working on import logic specifically. Real files are what actually
surfaced both of the bugs this fixture now guards against; if you're touching
`js/archimate.js`, re-test against a real file too, not just this fixture.

## Adding a new check

Write a function `check_something(page) -> (bool, str)`:
- `page` is a Playwright page already navigated to the running app (`window.dycadApp`
  is available).
- Do the setup and assertion via a single `js(page, "async () => {...}")` call where
  possible — keeps the check self-contained and fast.
- Return `(True, "short description of what passed")` or `(False, "what was wrong,
  with actual values")`. The detail string is what shows up in the failure output, so
  make it useful without needing to re-run anything by hand.
- Add the function to the `CHECKS` list in `run_all.py`.

Keep each check to one mechanism. A check that verifies five unrelated things makes
failures hard to diagnose — prefer more small checks over fewer large ones.

## What this suite deliberately doesn't do

- No visual/screenshot regression testing — DyCAD's correctness is almost entirely
  structural (data model, layout math, routing geometry), not pixel-level rendering.
- No coverage of every UI dialog end-to-end — a few checks exercise the underlying
  commands directly (faster, more stable) rather than clicking through every modal.
  Where a bug has actually involved the UI wiring itself (e.g. a button's id, a
  checkbox's default state), test that specifically when you touch it, but it doesn't
  need to live in this permanent suite unless it broke once already.
- No CI configuration — there's no build/deploy pipeline for this project yet. This is
  meant to be run manually before/after a change, and extended as new bugs get found
  and fixed, the same way each one already got a Playwright check written for it during
  development — this just keeps those checks around afterward instead of discarding them.
